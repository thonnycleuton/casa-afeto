# Casa Afeto — Technical Foundation

**Version:** 0.1
**Status:** Proposed
**Purpose:** Establish the initial technical foundation for the Casa Afeto system.

---

# 1. Purpose

This document defines the initial technical foundation for the Casa Afeto application.

Its purpose is to establish a stable technical direction before feature implementation begins.

The technical foundation should support:

* the current web application;
* incremental development;
* simple and maintainable architecture;
* automated testing;
* reliable persistence;
* future mobile clients;
* future AI-assisted document and receipt processing.

This document defines technical direction.

It does not define business rules.

Business behavior remains defined by:

```text
docs/domain/business-contract.md
docs/milestones/
```

---

# 2. Architectural Principles

The application should follow these principles:

### 2.1 Simple first

Use the simplest architecture that satisfies current requirements.

Do not introduce infrastructure for hypothetical future requirements.

### 2.2 Modular monolith

The initial application should be a modular monolith.

There is no current requirement for microservices.

Modules should have clear responsibilities, but remain inside one deployable application.

### 2.3 API-first backend

The backend should expose a clear REST/JSON API.

The web frontend consumes the API.

This also allows a future mobile application to consume the same backend.

### 2.4 Business rules belong to the backend

Critical business rules must not depend exclusively on frontend validation.

Examples include:

* inventory cannot become negative;
* inventory movements preserve history;
* sale confirmation requires sufficient inventory;
* payment rules.

The frontend may provide immediate user feedback, but the backend remains responsible for enforcing business invariants.

### 2.5 Database integrity matters

Persistent business data must be protected against invalid state.

Database constraints should be used where appropriate.

Application-level validation should complement, not replace, database integrity.

### 2.6 Test business behavior

Automated tests should focus particularly on business behavior and invariants.

# 3. Initial Technology Stack

## Backend

**Python**

Backend framework:

**FastAPI**

FastAPI will provide:

* HTTP API
* request validation
* response serialization
* OpenAPI documentation
* dependency handling where actually needed

Do not introduce additional backend frameworks unless a concrete requirement justifies them.

---

# 4. API

The initial API style is:

**REST + JSON**

The API should use conventional HTTP semantics.

The API should be documented through the OpenAPI specification generated by FastAPI.

No GraphQL implementation is required.

No RPC framework is required.

---

# 5. Database

Primary database:

**PostgreSQL**

PostgreSQL is the system of record for persistent business data.

The initial system should use a single PostgreSQL database.

No database-per-service architecture is required.

---

# 6. Persistence Layer

ORM:

**SQLAlchemy 2.x**

Database schema migrations:

**Alembic**

SQLAlchemy should be used where it simplifies persistence and domain interaction.

Do not create a generic repository abstraction merely because an ORM is being used.

A repository abstraction should only be introduced when a real problem justifies it.

---

# 7. Data Validation

**Pydantic** should be used for API input/output schemas and appropriate validation boundaries.

Business rules should not be reduced to schema validation.

For example:

```text
quantity must be a valid number
```

is input validation.

While:

```text
inventory balance cannot become negative
```

is a business invariant.

The latter must be enforced by the appropriate backend/domain logic and persistence strategy.

---

# 8. Frontend

Frontend framework:

**Vue 3**

Language:

**TypeScript**

Build tooling:

**Vite**

The frontend should communicate with the backend through the REST API.

The frontend should remain relatively thin.

Business-critical rules must not exist only in Vue components.

---

# 9. Frontend Testing

Frontend unit/component testing:

**Vitest**

Only introduce additional frontend testing tools when required by actual application needs.

---

# 10. Backend Testing

Backend testing:

**pytest**

Tests should emphasize:

* business rules;
* API behavior;
* persistence behavior;
* data integrity;
* important edge cases.

Tests should follow the conventions established in the project.

---

# 11. Containerization

Development environment:

**Docker / Docker Compose**

The initial containerized environment should primarily support:

* backend;
* frontend development where useful;
* PostgreSQL.

Do not introduce Kubernetes or other orchestration infrastructure.

---

# 12. Authentication

Authentication is not part of the current M1 scope.

The project should not implement a complete authentication/authorization system unless an actual requirement emerges.

The technical foundation should, however, avoid architectural decisions that would make future authentication unnecessarily difficult.

---

# 13. Future Mobile Application

A mobile application is a future requirement.

The current project does not implement mobile functionality.

The architecture should nevertheless preserve a clean API boundary so that a future mobile client can consume the backend.

This does **not** justify implementing mobile-specific abstractions now.

---

# 14. Future AI / Receipt Processing

The product is expected to evolve toward receipt/document ingestion.

A future workflow may resemble:

```text
Receipt image
      ↓
AI/document processing
      ↓
Extracted purchase data
      ↓
Human validation
      ↓
Purchase
      ↓
Inventory
```

This is not part of M1.

The current architecture should not implement an AI pipeline.

The only architectural consideration at this stage is to avoid coupling the inventory domain directly to a particular AI provider.

---

# 15. Architecture Style

The initial architecture should be a **modular monolith**.

Conceptually:

```text
                    ┌──────────────┐
                    │   Vue 3 UI   │
                    └──────┬───────┘
                           │
                         REST
                           │
                    ┌──────▼───────┐
                    │   FastAPI    │
                    ├──────────────┤
                    │   Modules    │
                    │              │
                    │ Products     │
                    │ Inventory    │
                    │ Baskets      │
                    │ Customers    │
                    │ Sales        │
                    │ Payments     │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │ PostgreSQL   │
                    └──────────────┘
```

Only modules required by the current milestone need to exist.

For M1, this means primarily:

```text
Products
Inventory
```

Do not create empty implementations for:

```text
Sales
Payments
Customers
Baskets
Purchases
```

simply because they appear in the future architecture.

---

# 16. Dependency Direction

The application should maintain a clear dependency direction.

Conceptually:

```text
HTTP/API
   ↓
Application / Business Logic
   ↓
Persistence
   ↓
PostgreSQL
```

The exact implementation structure may vary based on the existing project and implementation analysis.

Do not create unnecessary layers merely to satisfy this conceptual model.

---

# 17. Error Handling

The backend should provide consistent application errors.

Errors should distinguish, where appropriate:

* invalid input;
* resource not found;
* business rule violation;
* persistence failure;
* unexpected internal failure.

Internal implementation details should not be unnecessarily exposed through the API.

---

# 18. Configuration

Environment-specific configuration must not be hard-coded.

At minimum, configuration should support separation of:

* development;
* test;
* production.

Secrets must not be committed to source control.

The implementation should follow established environment-variable conventions.

Do not introduce a complex configuration framework unless necessary.

---

# 19. Database Migrations

All schema changes must be represented through the project's migration mechanism.

For PostgreSQL:

**Alembic**

A developer should be able to:

1. create a fresh database;
2. run migrations;
3. start the application;
4. execute the automated tests.

The migration history should remain reproducible.

---

# 20. Code Quality

The project should use automated formatting and linting appropriate to the selected stack.

However, tooling should remain proportional to project needs.

Do not spend significant development effort configuring a large collection of static-analysis tools before there is a concrete benefit.

The primary priorities are:

1. correctness;
2. maintainability;
3. tests;
4. consistency;
5. readability.

---

# 21. Architecture Decision Records

Significant architectural decisions should be documented under:

```text
docs/architecture/decisions/
```

Examples include:

* changing the database technology;
* introducing a major architectural pattern;
* introducing a new external infrastructure dependency;
* replacing a core framework;
* introducing asynchronous processing for a concrete requirement.

Not every implementation detail requires an ADR.

---

# 22. Technology Change Policy

The stack defined here is the approved initial direction.

An agent must not replace a technology because another technology appears newer, more popular, or personally preferable.

A stack change requires:

1. identification of the problem;
2. explanation of why the current technology is insufficient;
3. alternatives;
4. impact analysis;
5. human approval.

---

# 23. M0 Definition of Done

The technical foundation is considered established when:

* [ ] Backend project can start.
* [ ] Frontend project can start.
* [ ] PostgreSQL can run locally.
* [ ] Backend can connect to PostgreSQL.
* [ ] Database migrations work.
* [ ] A basic automated backend test runs.
* [ ] A basic frontend test runs.
* [ ] API documentation is available.
* [ ] Development configuration is documented.
* [ ] Secrets are not committed.
* [ ] Docker-based development environment works, where applicable.
* [ ] Project structure is documented.
* [ ] No feature from M1 has been implemented merely as part of M0.
* [ ] The project can be handed to another developer/agent and started without undocumented manual steps.

---

# 24. Relationship with Product Development

M0 establishes the technical foundation.

After M0 is accepted:

```text
M0 — Technical Foundation
        ↓
M1 — Products & Inventory
        ↓
M2 — Baskets & Basket Templates
        ↓
M3 — Customers
        ↓
M4 — Sales
        ↓
M5 — Payments
```

M0 must not become a reason to delay product development indefinitely.

The goal is to establish enough foundation to build M1 safely, not to design the entire future system.

---

# 25. Guiding Principle

> Choose enough technology to build the product well.

Not:

> Choose technology for every product we might build someday.

The architecture should support future evolution without requiring us to implement that future today.
